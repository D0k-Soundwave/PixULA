# Feature: Undo depth setting (owner decision 2026-10-19)

ZX Paintbrush lets the artist set how many steps Undo keeps. PixULA keeps 500 and has no
setting. Owner decision 2026-10-19: a Preferences setting, 1 to 2000 steps, default 500.
The 256 MB memory cap (UndoRedoManagerClass.MAX_HISTORY_BYTES) stays, and the setting's
hint says that on a big picture the cap can keep fewer steps than set.

## Data shape

- js/core/constants.js: ZX_SPECTRUM.MIN_UNDO_LIMIT = 1 and MAX_UNDO_LIMIT = 2000 beside
  DEFAULT_UNDO_LIMIT = 500 (all three owner decision 2026-10-19; FIGURES.md rows).
- Validators.isValidUndoLimit: integer in MIN..MAX (was 1..500). Callers: UndoRedo.initialize
  (stored value at boot) and UndoRedo.setMaxStates. No test relied on 500 as a maximum
  (undo-snapshot.spec.js sets maxStates = 500 directly, input-touch.spec.js sets 3).
- Stored under the existing key 'pref.undoLimit' (Storage, PREFERENCES store), written by
  setMaxStates - not in the 'preferences' record, so nothing else that writes that record
  can clobber it. Reset All Preferences deletes it.
- UndoRedo.setMaxStates(n): refuses anything invalid; sets the depth, prunes at once
  (lowering drops the oldest steps; the redo stack is untouched, as before), returns a
  promise that resolves true once stored (false if refused or the write failed), so the
  dialog can wait for the write like the rest of _save. getMaxStates() added.
  initialize() returns its promise and prunes after loading the stored depth.
- Preferences dialog, General section: number field #pref-undo-limit (min 1, max 2000,
  step 1) labelled pref.undoLimit, hint pref.undoLimitHint with {min} {max} {mb}
  placeholders (data-i18n-param-*). OK clamps a typed value (Helpers clamp, as the other
  fields), empty keeps the current depth; it writes only when the value changed, so an
  untouched dialog stores nothing. Cancel changes nothing.

## Screen modes

The history is the same in every mode (a snapshot of the whole document, the mode
included), so the setting applies identically in Standard ULA, GigaScreen, ULAplus,
ULANext, Timex hi-res and its pair, multicolour, Layer 2 and LoRes. What differs by mode
is only how many steps the 256 MB cap allows: 8,448 B a one-layer step at STANDARD_ULA
against 212,480 B at LAYER2_640 (M, 2026-08-07), so 2000 steps is ~16.9 MB at Standard
ULA (C: 2000 x 8,448) but ~425 MB at LAYER2_640 (C: 2000 x 212,480), over the cap, where
~1,263 one-layer steps fit (C: 268,435,456 / 212,480). That is what the hint warns about.
Nothing to hide or refuse in any mode.

## Tests (written first, seen failing)

- tests/undo-depth.test.js (Node): the range constants; isValidUndoLimit 1..2000 (0, 2001,
  1.5, '600' refused); setMaxStates(1500) accepted and stored; 2001 refused and not stored;
  lowering from 20 steps to 5 keeps exactly the newest five at once; the byte cap still
  prunes below a 2000 depth (not below MIN_HISTORY_ENTRIES); initialize() honours a stored
  1500 and prunes to a stored lower value; the en hint names {min} {max} {mb}.
- tests/browser/undo-depth.spec.js: the field shows 500 with min 1 / max 2000 and the hint
  names the 256 MB cap; setting 1500 survives a reload; lowering to 4 after 12 steps keeps
  4 at once and Undo stops after 4; typed 5000 becomes 2000 and 0 becomes 1; Cancel
  changes nothing; Reset All Preferences returns it to 500; depth 3 holds in Layer 2 640,
  LoRes, Timex hi-res and GigaScreen; the German hint has its numbers filled in.
